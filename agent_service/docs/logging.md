# Журнал запросов и диагностика провайдера

## Обычный режим

Каждое событие — одна строка в stdout. Во всех логах внутри обработки запроса
добавляются chat_id и request_id; внутри цикла — iteration (с нуля), попытка
LLM — attempt (с единицы), инструмент — tool_call_id. Контекст изолирован через
ContextVar, включая параллельные вызовы инструментов. Сброс выполняется в finally.
События:

- request.start / accepted / answer / end — вход и доставка, длительность;
- agent.start / model / final / end — выбранная модель, число шагов и инструментов;
- llm.start / attempt / retry / fallback / result / tokens — SDK и учёт токенов;
- llm.http.request / response / end — фактический HTTP после преобразований SDK;
- tool.start / invoke / result / end — имя, ID, длительность, результат/ошибка.

Полные промпты, аргументы, результаты инструментов, reasoning и signatures не
печатаются новым логгером в INFO. Содержимое представлено длинами и SHA-256.
Старые сообщения обрезаются до 1800 символов и превращаются в одну строку.
Секретные поля, Bearer и известные ключи окружения редактируются. Это защитная
мера, не гарантия автоматического распознавания всех возможных личных данных.

Параллельно пишется JSONL по UTC-дням: /tmp/agent-logs/20_11_2026.jsonl.
Текущий день и 6 предыдущих (7 календарных UTC-дней), максимум 500 МиБ
(524288000 байт) суммарно. Приоритет у объёма: сначала удаляются старые дни,
если один день больше бюджета — его старейшие строки (с запасом 10% бюджета, чтобы не перезаписывать
500 МиБ при каждой следующей записи). JSON-строки не разрезаются;
одна запись больше всего бюджета пропускается. Очистка при старте, записи и
каждые 60 секунд даже без запросов. Блокировка flock поддерживает несколько
процессов в одном каталоге. Лимит относится к JSONL-файлам; служебный lock
и кратковременный файл потоковой перезаписи не входят в него.
Старые events.jsonl и events.jsonl.N тоже учитываются и чистятся, но не переименовываются.
Файлы имеют права 0600, новый каталог 0700. Каталог задаётся AGENT_LOG_DIR;
пустая строка отключает файл. При недоступном диске обработка не прерывается.
AGENT_LOG_LEVEL задаёт уровень. Сторонние httpx/httpcore INFO отключены.
Compose подключает bind mounts из корня проекта; без них /tmp теряется при пересоздании.

HTTP request содержит хеш тела, размеры и хеши каждого сообщения, роли, имена
инструментов, хеш последнего user и current_query_present — присутствие исходного
user_input в фактически отправленных messages. null означает, что исходная строка
для сравнения недоступна; false требует проверки и само по себе не доказывает баг.
Нативное Anthropic system учитывается отдельно. HTTP response содержит status и
provider_request_id; HTTP end — байты, SHA-256 сырого тела, EOF и терминатор SSE.
Границы чанков и транспортные ошибки передаются SDK без изменения.
Gzip/deflate инспектируются отдельным декодером. Для неизвестного кодирования
incomplete_sse=null; decode_error=true. Нестримовый JSON не считается оборванным SSE.
SDK result позволяет сопоставить реальные tool use с распарсенными tool_calls и
числом invalid_tool_calls. suspicious_empty_claim — лишь флаг для расследования:
он НЕ меняет ответ, не выполняет ретраи и не доказывает потерю tool call.

## Диагностический режим

В окружении agent_service (compose уже пробрасывает эти параметры):

```dotenv
AGENT_DIAGNOSTICS_CHATS=425826,6b5e307d-8ab4-47f0-86e6-ae6a4d9cda13
AGENT_DIAGNOSTICS_DIR=/tmp/agent-diagnostics
AGENT_DIAGNOSTICS_MAX_BYTES=2097152
AGENT_DIAGNOSTICS_MAX_TOTAL_BYTES=52428800
AGENT_DIAGNOSTICS_TTL_SECONDS=86400
```

Потребуется пересоздать контейнер для изменения окружения. Не включать для всех
чатов: '*' не поддерживается намеренно. По умолчанию режим выключен.

Для каждого HTTP — request.json и response.json, связь через http_id, chat_id,
request_id, iteration, attempt. Имя файла — UUID, а не пользовательский путь.
Authorization и остальные заголовки целиком не сохраняются. Только безопасные
идентификаторы ответа и content-type. Содержимое JSON/SSE редактируется:
signature/password/api_key и известные ключи окружения удаляются. Поэтому capture
не побайтная копия; sha256 и response_bytes — от исходных сетевых байтов.

Буфер ответа ограничен MAX_BYTES, файл записывается при завершении/закрытии потока.
При kill -9 незакрытый ответ может не сохраниться. EOF, sse_terminal,
capture_truncated, error_type различают нормальный конец, обрыв и усечение.
Один файл не больше MAX_BYTES; если метаданные и сериализация не помещаются,
тело опускается или файл пропускается. Общий бюджет ограничен MAX_TOTAL_BYTES.
Очистка по TTL и бюджету выполняется при записи следующего capture, не фоновым
таймером. Минимум числовых лимитов — 1024. Захваты содержат приватную историю,
доступ только оператору. Не раздавать каталог через web. После расследования
выключить параметр и удалить выгрузки. Для строгой длительности хранения нужен
внешний scheduled cleanup. Бюджет синхронизирован в пределах процесса; при
нескольких worker-процессах использовать отдельный каталог на worker.

## Выгрузка

Извлечь без печати истории в терминал:

```bash
docker cp agent_service:/tmp/agent-logs ./agent-logs
docker cp agent_service:/tmp/agent-diagnostics ./agent-diagnostics
```

Фильтр журнала по чату/запросу:

```bash
jq -c 'select(.chat_id=="425826" and .request_id=="REQUEST_ID")' agent-logs/*_*.jsonl
```

Искать цепочку HTTP request → response → end → llm.result с одним http_id/шагом.
При обрыве до HTTP response request-id провайдера может отсутствовать; исключение
и повтор останутся в llm.retry. После этого собрать request/response captures и
связанные JSONL-строки; проверить приватные данные перед отправкой провайдеру.
EOF без message_stop/[DONE] — признак неполного SSE, а не автоматическое доказательство
общей причины с текстовым финалом «пустой запрос».

## Постоянное хранение в корне проекта

Compose монтирует ./agent-logs → /tmp/agent-logs и
./agent-diagnostics → /tmp/agent-diagnostics. Они сохраняются при пересоздании
контейнера; оба исключены из Git и Docker build context. Диагностика остаётся
opt-in, с прежними лимитами 24 часа / 50 МиБ / 2 МиБ на файл; её TTL-очистка
по-прежнему выполняется при записи capture, а не отдельным таймером.

Перед первым запуском из корня проекта подготовить каталоги для UID/GID 1002
(пользователь appuser в образе; если переопределён user — использовать его UID):

```bash
sudo install -d -m 0700 -o 1002 -g 1002 agent-logs agent-diagnostics
docker compose up -d --build agent_service
```

Существующие файлы из старого контейнера при необходимости сначала выгрузить:
bind mount не переносит их автоматически. Не раздавать эти каталоги через web.
По умолчанию пути в контейнере совпадают с mounts; при переопределении
AGENT_LOG_DIR / AGENT_DIAGNOSTICS_DIR нужно согласовать и volumes.

Настройки: AGENT_LOG_DIR, AGENT_LOG_RETENTION_DAYS=7,
AGENT_LOG_MAX_TOTAL_BYTES=524288000. Устаревший AGENT_LOG_JSONL поддерживается
при прямом запуске: используется только его родительский каталог.
JSONL можно полностью отключить через AGENT_LOG_DIR="" при прямом запуске.

```bash
jq -c 'select(.chat_id=="425826")' agent-logs/*_*.jsonl
```

Ограничение 500 МиБ относится к журналу событий, а не к stdout Docker.
Настройки Docker logging driver эта правка не меняет.
