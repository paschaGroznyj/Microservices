# Активная сессия Telegram и MAX

Источник истины — PostgreSQL: `telegram_chat_settings.current_session_id` и
`max_chat_settings.current_session_id` (TEXT). Значение — UUID сессии либо
физический ID этой же группы: под ним лежит корневая история группы, созданная
до появления сессий. Если поле NULL, по умолчанию берётся именно он: группа
продолжает ту историю, в которой жила до миграции. ID другой группы и
произвольные строки отклоняются (422).
Физический ID группы — ключ строки настроек и адрес доставки.

GET `/{tg|max}/session/{physical_chat_id}` читает активный UUID.
POST с `session_id` явно выбирает UUID (меню); POST с `only_if_unset: true`
атомарно инициализирует его, не перезаписывая конкурентный выбор. Если
session_id не передан, записывается физический ID группы; новые UUID создаются
только меню через /chat/new. Неизвестные/неактивные группы — 404.
Ошибка БД/API останавливает dispatch без переключения контекста.

## Развёртывание и перенос

1. Сохранить Redis/AOF перед обновлением, НЕ очищать старые session-ключи.
2. Сначала обновить chats_service. При запуске добавляет nullable UUID-колонки
   через идемпотентный ALTER; SQL bootstrap также содержит эту миграцию.
3. Затем обновить MAX и Telegram. При первом обращении, только если поле БД NULL,
   бот переносит старый UUID из `tg:session:<id>` / `max:session:<id>` через
   атомарный only_if_unset. В дальнейшем Redis для маршрутизации не читается.
4. Старое значение, равное физическому ID группы, переносится как корневая
   история. Если оно не UUID и не ID этой группы, запрос останавливается:
   оператор должен выбрать сессию в меню.
5. Если старой привязки нет (в т.ч. ключ вытеснен), записывается физический ID
   группы — корневая история до появления сессий. Новый пустой UUID при
   миграции не создаётся. Если группа до потери ключа работала в другой
   выбранной сессии, её нужно один раз выбрать в меню.

Redis остаётся для других функций ботов, списка/подписей сессий меню и
одноразового переноса старой привязки; активный UUID не кешируется в Redis.
Меню новой/существующей сессии сохраняет выбор в БД до подтверждения.
При первом создании/переносе UUID регистрируется также в кеш-реестре меню.
Триггеры и пользовательские сообщения используют одну функцию разрешения.

Обновить все три сервиса; новые боты со старым chats_service не работают
(404 вместо незаметного fallback). Для rollback сначала вернуть боты, затем
chats_service; старый Redis-ключ после переключений в новой версии может быть
устаревшим, его нужно восстановить из БД вручную. Nullable-колонки не удалять.

Колонка 0006bc4 была UUID и роняла выбор корневой истории в меню
(`badly formed hexadecimal UUID string`). Startup chats_service и SQL bootstrap
идемпотентно переводят её в TEXT с сохранением значений.
