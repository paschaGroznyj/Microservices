# Потоковая передача ответов и рассуждений моделей

В режимах «Агент» и «Модель» фрагменты потока провайдера передаются до завершения
генерации. Для полей reasoning_content/reasoning OpenAI-совместимых моделей и
блоков thinking Anthropic используются события `live` / `reasoning_end`.
ReasoningCleaner удаляет Markdown, не обрезая пробелы по краям каждого фрагмента.
ContentStreamRouter разделяет видимые рассуждения thinking, скрытые рассуждения
reasoning и текст ответа, даже если границы тегов попадают на стыки фрагментов.
Фрагменты аргументов вызова инструментов в браузер не передаются.

## События потока

- `live`: очередной фрагмент видимых рассуждений.
- `reasoning_end`: закрытие открытого блока рассуждений; допускается пустой фрагмент.
- `answer_delta`: фрагмент предварительного ответа на текущем шаге модели.
- `answer_reset`: сброс предварительного ответа при повторной попытке или вызове инструмента.
- `answer_end`: полный итоговый снимок ответа после закрытия всех блоков рассуждений.
- `final_commit`: перевод ответа из предварительного в финальное отображение; событие done из Kafka обеспечивает сохранение и передачу файлов.

Основной WebSocket и связка Redis/SSE в Sigma передают одинаковые типы событий.
Фронтенды хранят предварительный ответ отдельно от рассуждений для каждого чата,
показывают весь накопившийся текст один раз за кадр анимации и не планируют новые
кадры, если обновлений нет. Финальный текст из Kafka имеет приоритет над
предварительным ответом. Структурированные JSON-компоненты по-прежнему обрабатывает
существующий потоковый парсер. Для Markdown в ответах используется прежний
рендерер: полноценного инкрементального разбора Markdown нет, поэтому длинные
ответы могут сильнее нагружать процессор.

## Совместимость и ограничения

Экранированные XML-обёртки thinking/reasoning и обёртки в обратных кавычках
буферизуются до окончательного разбора шага. Обычные блоки кода Markdown
передаются потоком, как только их префикс можно однозначно отличить от такой
обёртки. Содержимое незакрытого блока скрытых рассуждений никогда не попадает
ни в потоковый, ни в финальный текст ответа.
Redis сохраняет рассуждения, но не фрагменты предварительного ответа. Поэтому
после переподключения часть ответа может отсутствовать до следующего полного
снимка answer_end или финального сообщения.
При принудительном достижении жёсткого лимита путь ainvoke остаётся резервным
вариантом с получением сообщения целиком.
Модульные и UI-тесты не подтверждают сквозную работу Redis/Kafka в продакшене.

## Тесты

Запускать из корня репозитория, предварительно установив зависимости сервисов:

```bash
PYTHONPATH=agent_service:agent_service/app python -m pytest \
  agent_service/tests/test_live_streaming.py \
  agent_service/tests/test_not_loop.py \
  agent_service/tests/test_reasoning_pipeline.py
PYTHONPATH=api_gateway python -m pytest \
  api_gateway/tests/test_flow_stream.py \
  api_gateway/tests/test_answer_stream_state.py
PYTHONPATH=.:api_gateway python -m pytest api_gateway_sigma/tests/test_stream_transport.py
STREAM_TEST_DEPS=$(mktemp -d)
npm install --prefix "$STREAM_TEST_DEPS" --no-save --package-lock=false jsdom@24.1.3
NODE_PATH="$STREAM_TEST_DEPS/node_modules" node api_gateway/tests/streaming/stream-integration.cjs
rm -rf "$STREAM_TEST_DEPS"
```

Набор тестов jsdom загружает реальные классы из app.js/app_sigma.js, подменяя
транспорт и Markdown-рендерер. Браузерная приёмка дополнительно проверяет настоящий
рендерер, CSS, DOMPurify, GenerativeUI и кадры анимации в светлой и тёмной темах
на настольных и мобильных экранах.
